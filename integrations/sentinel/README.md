# Microsoft Sentinel

1. Create the custom table `RoboDRFindings_CL` from
   `RoboDRFindings_CL.table.json` (`PUT .../tables/RoboDRFindings_CL`).
2. Create the data collection rule from `dcr-robodr-findings.json` (fill in
   `<region>` and the workspace resource id). Its transformation keeps the
   whole finding in `RawFinding` and projects the typed columns; tainted DDS
   names only in their escaped `display` form.
3. Send findings through the Logs Ingestion API. Findings nothing verified
   (Azure Event Hubs' Kafka endpoint, or Logstash with the
   `microsoft-sentinel-log-analytics-logstash-output-plugin`) go to stream
   `Custom-RoboDRFindingsRaw`: it does not declare `robodr_verification`,
   so `VerificationStatus` is empty whatever the finding carries (a forger
   chooses every field). Output of `integrations/verify/robodr_verify.py`
   goes to `Custom-RoboDRFindingsVerified`, where the verifier's
   `robodr_verification.status` becomes `VerificationStatus`. Nothing here
   wires the verifier into the Event Hubs or Logstash-output path. The DCR
   cannot tell senders apart: only the verifier's sender may use the
   verified stream.
4. Save `RoboDRFindings.kql` as a workspace function named `RoboDRFindings`.
5. Import the scheduled analytics rules in `analytics/` (generated by
   `integrations/gen_detections.py`). Observe-only. The five shared rules
   drop findings whose `VerificationStatus` is set and not `verified`;
   `unverified-findings.yaml` reports every finding that is not verified,
   including those with an empty status.

Checked by `integrations/check_content.py` (DCR columns against the table,
the two streams' transformations identical but for `VerificationStatus`,
contract fields, rule ids, columns used by the rules and the parser). Not yet
deployed in a Sentinel workspace; the KQL has not been run.
